# Session Transcript: v1.1 Layers 0–3 UF2 Flash

## Request

Copy the new four-layer B1 Pro firmware to the ready test unit.

## Evidence

- Revision: `v1.1_Layers0-3`.
- UF2: `build-spec-layers-0-3/zephyr/zmk.uf2`.
- Size: 427,520 bytes.
- SHA-256:
  `9a7efd0de6c86e7a0cdb1a0a1d29e67611cdde0a0c5ddeee5905661b67d87a55`.
- Target confirmed immediately before transfer: `E:` with volume label
  `NRF52BOOT`.

## Action and Result

The exact UF2 was copied to `E:\zmk.uf2`. Windows reported `1 file(s)
copied.` The `E:` volume then disappeared, which is the expected host-side
completion signal for a UF2 bootloader flash.

## Hardware Result

Hardware acceptance failed. The physical Mac/Win-switch matrix position was
incorrectly bound to `&mo LAYER_FN_NUM`, so an active switch position held the
keyboard in the Fn layer. That made the Layer 1 bindings override modified
base-layer keys, including making the physical minus key invoke the Boot
hold-tap behavior instead of typing minus.

## Follow-up

Recover the unit through the hardware bootloader, then restore a known-good
factory image before deploying a corrected custom build. This record verifies
the transfer and bootloader exit only; it does not claim functional keyboard
validation.

## Workflow Recommendation

No new standalone skill is needed. The existing local-builder workflow remains
the appropriate future home for repeatable build, revision registration, UF2
detection, transfer, and post-flash verification.
